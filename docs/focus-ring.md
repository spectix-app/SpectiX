# 跳转落点高亮圈（FocusRing.swift）

跳转（快捷键/点行/点 toast）落到 VSCode 后，在**目标会话的 terminal pane** 上叠一圈发光描边（颜色 = 会话状态色），**呼吸三下（~3.8s）后顺着节奏淡出**——不硬切呼吸半程；再次点击跳转会重画并重新开始三下。敲键盘提前消；找的过程中点别的 terminal 圈不消也不挪。

- **★ 「常驻显示」开关（`ringAlwaysOn` = always-on 托管圈）是 dev-only（`Build.isDev`，`Pro.swift`）**：只有 `./build.sh` 带 `-D DEV_BUILD` 编出的本地版才有这一行设置（标题旁挂 `DEV` 徽章）；`package.sh` 的发布路径（`UNIVERSAL=1`）不带该 flag → 发布版**根本不建这一行**，且 `AppSettings.ringAlwaysOn` 恒读 false（getter 上的门），FocusRing 里所有 always-on 分支（托管 overlay / `recolorOverlays` / `kickRescan`）随之全不跑，`defaults write` 也翻不出来。理由：常驻扫描是全 App 最贵的一条路（持续爬 VSCode AX 树），recolor 台账又是历史 bug 高发区，稳定前不发给用户。⚠️ **别和 caption 的「常驻显示」混**——那是 `captionDuration == .forever`（下面几条讲的那个），**不受影响**，发布版照常有。
- **pane 定位**：VSCode 是 Electron，渲染层 a11y 树默认收起（focused-element 查询返回 NoValue）。对其设 Electron 专属 `AXManualAccessibility` 展开树后，`kAXFocusedUIElementAttribute` 会落在 xterm 的隐藏输入框（`AXDOMClassList` 含 `xterm-helper-textarea`，**用 class 判定不用 desc**——desc 是本地化文案）。该元素只有光标大小（~7×14），沿 `kAXParent` 走到第一个有实际尺寸（≥100×40）的祖先就是 `.xterm-screen` = pane 的屏幕 frame。首次展开要 1-3s，故 **App 启动时 `prewarm()` 预展开**，跳转时基本首查即中。**故意不关** `AXManualAccessibility`：反复开关会每次重触发 VSCode 的屏幕阅读器提示 + 整树重建。
- **★ 跳转的圈/标签「0s 出现」：记忆预绘 + 实测校正（T148，改 `paneMemo` / `recallPane` / `present` 的 `predicted` 分支 / `armPredictionGuard` 前必读）**：跳转的圈原本要等三件事**串行**跑完才画得出来——① `raiseEditorWindow` 的 AX IPC；② extension 收到 focus-request 后跑 `term.show` 并写 `active-terminal` token；③ Electron 的 AX 树把焦点更新到那个 pane——下面「身份对账」的三重判据才成立，实测 ~250-450ms（用户报「点了以后高亮和标签慢一点」）。但这段等待回答的**只有「在哪」，从来不是「圈谁」**：target shellPid 是点击那一行给的，第一瞬间就确切。而「在哪」**上次圈它时就量过**——pane 只在窗口移动/改大小/分栏重排时才换位置。
  - **修法**：`present` 每次**实测**成功就把 `(pane AX rect, 宿主窗口号, 该窗口当时的 CG bounds)` 记进 `paneMemo[shellPid]`（`track` 每 ~2s 刷 anchor 时顺手更新，所以拖完窗口马上跳也准）。下次 `highlight(fromJump: true)` **在 poll 之前**先 `recallPane` 查记忆，命中就立刻 `present(..., predicted: true)` —— **0ms 上屏**；poll 照常跑，确认后再 `present`（predicted 默认 false）**走 reposition 而不是 show**（`window != nil` 分支），位置没变就 no-op，变了就滑过去。**不重建 overlay** 是硬要求：`show()` 会重启呼吸动画并重排 teardown 定时器，圈刚出现就抖一下。
  - **`recallPane` 三道闸**（全部围绕「记住的矩形可能已经不作数了」）：① **TTL 30min**；② **宿主窗口仍在 onscreen 列表**——`CGWindowListCopyWindowInfo(.optionOnScreenOnly)` 只列**当前 Space** 的窗口，所以这道闸顺带把预绘**限定在同 Space 跳转**（跨 Space 本来就要等切换动画，且在切过去之前按目标的绝对坐标画，圈会落在你正要离开的那个 Space 的随机位置上，`bindToActiveSpace` 还会把它绑到**错的** Space）；③ **该窗口 bounds 与记录时一致**——窗口移动/改大小会重排里面每一个 pane，正是记忆失效的主因。**漏网的只剩「窗口没动但分栏变了」**，交给下面的撤回兜底。
  - **★ 撤回必须「撤 + 重跑」，不能只撤（改 `armPredictionGuard` 前必读）**：预绘是没验证过的断言，poll 2s 内没确认就得收回（「圈错比不圈更糟」）。但 `dismiss()` **会 bump generation**，而 generation 正是 poll 中止的判据——只撤不重跑 = 把还在跑的解析一起杀掉，于是「pane 只是慢了点」的跳转最后**什么都不显示**，比它要消灭的那段等待更糟。故撤回 = `dismiss()` → 重新 `armDismissListeners()`（dismiss 刚把它们卸了）→ 用新 generation 从 `attempt 0` 重跑 poll，把 highlight 交还给「预绘之前」那个状态。**`armedAt` 故意不重新打点**：token 是这次跳转写的，`freshFocusReport` 的 mtime 闸必须继续认它。
  - **只给跳转**（`fromJump`）：手点终端时焦点本来就在那个 pane 上，poll 第一 tick 就中；paused/interrupt 的自发闪烁（`strictToken: false`）根本不是用户瞄准的，更不该预绘。
  - **★ 记忆要主动预热，别只等圈画出来才有（`warmPaneMemo` / `scanPanes`，改这两个前必读）**：只靠「画圈时顺手记」的话，**第一次**跳到某个 pane 仍然全价等 ~250-450ms —— 而对一个刚起的会话来说，「第一次」就是绝大多数次。可那次测量根本不需要等点击：你在编辑器里干活的时候，它的终端布局就摆在那里可以读。故 `main.refresh()` 每轮调 `warmPaneMemo(rows:)`，把 always-on 那套测量（`scanPanes`，从 `rescanAlwaysOn` 抽出来共用）跑一遍只写 memo、不建 overlay。三道闸让它不至于变成后台负担：① **真有 cold 的**（本编辑器名下某个会话 `recallPane` 拿不到）才扫——稳态下每个 pane 都热，这条路的成本是「每个会话一次字典查询 + 零 AX 调用」；② **编辑器在前台**才扫（跳转将至的时刻，也正是聚焦窗口的树就是你会跳进去的那棵）；③ 3s 节流，挡住「解析不出的 pane → 每轮重扫」的死循环。always-on 开着时整个函数直接 return（`rescanAlwaysOn` 自己已经在写 memo）。实测 CPU：基线 23% vs 带预热 24%（30s 窗口，噪声级差异）。
  - **★ 预热扩到编辑器的其它窗口（`sweepOtherWindows`，T157，改这块前必读）**：`scanPanes` 的入口是**聚焦元素**再往上走，所以它天生只看得见聚焦窗口那棵树 —— 跳进任何别的窗口的 pane 仍然全价等 ~250-450ms。但那些 pane 并非不可知：它们的窗口就摆在那里。故聚焦窗口扫完还有 cold 的，就把其余窗口交给 `sweepOtherWindows`：**没有聚焦元素可当入口，容器得靠遍历窗口的树找出来**（`findTerminalContainers`），这是贵的一条路，所以用**五道闸**围住：① 只在聚焦窗口扫完**仍有 cold** 时才走（稳态「要跳的都在眼前这个窗口」根本到不了这里）；② `sweepInterval` 30s 叠在 warmInterval 的 3s 上，外加**每窗口退避**（空手而归就 30s→1m→2m→封顶 5min；该窗口被挪动/改尺寸、或 cold 集合变了就清零重来，因为「答案可能变了」）；③ **只扫同 Space**（`.optionOnScreenOnly` 本就只列当前 Space，而这恰好就是 recall 闸 ② 允许预绘的范围，扫 Space 外的 pane 是没人花得掉的功）；④ 每轮最多 3 个窗口、front-to-back（下一个要跳进去的多半就是紧挨着的那个），且压在 0.4s 硬墙钟预算下，AX 走慢了就**放弃、绝不排更深**；⑤ 跳转在飞的时候不扫（sweep 排在 poll 前面会拖慢它本要省掉的那次解析）。**身份照旧不猜**：没有聚焦 pane 就没有 token 可学，只有唯一名字或该窗口已学到的 pin 才解析得出，其余保持 cold 走老路 —— 和以前一样，只是少得多。
    - **★ memo 的宿主窗口必须是「真扫的那个」，不许从矩形反推**（`rememberScanned`）：`editorWindowInfo` 取的是「bounds 包住 pane 中心的最前面那个窗口」——只扫聚焦窗口时这没问题（它按定义就是最前的），但背景窗口的 pane 若被另一个 VSCode 窗口压住，就会被记到**压在它上面的那个窗口**名下；而 `recallPane` 三道闸会全部通过，于是预绘把圈画到别人窗口的内容上——**圈错比不圈更糟**。扫描本来就知道窗口 id，直接传进去；反推只留作拿不到 id 时的兜底。
    - **manifest 按文件拆开、不只合并**（`loadManifests` / `windowManifest`）：extension 每个窗口写一份（`terminals-<extHostPid>.json`，每个 VSCode 窗口跑各自的 extension host），所以**按文件拆 = 按窗口拆**。背景窗口那些同名 `✳ Claude Code` 之所以还解析得出来，靠的就是先把候选缩到该窗口自己那份 manifest 里。窗口→文件的绑定从「已解析出的 pane 的 pid」学（pid 系统内唯一，所以这是证据不是猜），且只在**聚焦窗口**学（那里的解析有 token 背书，最可信）；窗口重载会换 extension host = 换文件名，故 `pruneWindowManifest` 每轮清掉失效绑定，否则旧绑定会查不到任何候选、悄悄不再解析。
    - **⚠️ CPU 复测尚未做（T157 遗留，谁先碰这块谁补）**：`warmPaneMemo` 的第一道闸是**编辑器在前台**（`frontmostEditorApp()` 要求 `isActive`），而**锁屏时 `isActive` 恒 false**（前台归 `com.apple.loginwindow`），且 `.optionOnScreenOnly` 列不出任何窗口 → 整条 sweep 路径在无人值守/锁屏下**根本不执行**，测出来的数字只反映休眠态（实测 40s 静息 avg 7.7%，与本功能无关）。要测得摆出真实条件：**解锁屏幕 + 至少 2 个各自有 Claude 会话的 VSCode 窗口 + 编辑器置于前台**，重启 App（`paneMemo` 纯内存，重启即全 cold）后读上面那个日志的 `<耗时>ms`，并对照 `warmPaneMemo` 那条的 23% 基线跑一次 30s 窗口。
    - **诊断日志**：`~/.claude/spectix/focusring-sweep.log`，每轮一行 `windows=<扫了>/<候选> panes=<预热到> <耗时>ms`（自清于 128KB）。**无条件写**且候选数和实扫数并列——只在 `swept > 0` 时写的话，「跑了但没窗口可扫」（全在退避中，或**锁屏时 CGWindowList 的 onscreen 列表为空**）和「压根没跑」长得一模一样，这正是它要防的误诊。⚠️ 别把埋点加到 `warmPaneMemo` 顶部：那里跑在**主线程**、且由 `refresh()`（2.5s 定时器 + FSEvents）驱动，实测**每秒约 25 行**主线程写盘。
  - **仍走老路的情况**（不猜）：目标 pane 在**别的 Space**（recall 的 onscreen 闸）、窗口刚被挪动过（bounds 闸）、或该 pane 所在窗口这轮还在 sweep 的退避期内。
- **★ 身份对账（防「圈错 terminal」——改这块前必读）**：聚焦元素 = 「当下焦点碰巧在哪」，**不等于目标**——extension 的 `term.show` 和用户手点别的 terminal 有竞态，光认 focused textarea 会圈到用户刚点的那个（v1 的 bug）。判据**三重**：① **extension 写的 `active-terminal`（`<shellPid>:<nonce>`，每次终端聚焦都写）报的 pid == 目标 shellPid** 且 **mtime 是本次跳转的新写入**（≥ armedAt−3s，宽限是因为 extension 可能在 `raiseEditorWindow` 期间、armedAt 打点之前就写了）；② focused 元素是 xterm textarea；③ **pane 归属验证 `paneOwner`**——①②会各说各话：Electron 的 **AX 树更新滞后于 token 写入**，`term.show` 后 token 已报目标、`kAXFocusedUIElement` 还停在上一个 terminal 的 textarea，①②同时满足但描述两个 pane（「圈先亮旧 terminal 再滑过去」bug 的根因）。故读 focused pane 自己的标题（`paneTitle`）经 terminals manifest 反查 shellPid **必须命中目标**；标题解析不出（非 Claude pane / 未知 locale）算「无证据」退回①②，反查出别人 → 继续轮询。对不上 → 继续轮询（pane 路径前 8 tick 0.12s 快步进、之后 0.25s，最多 ~6s，用户找的途中点回正确 terminal 时圈会亮出来当确认），**绝不圈别人**。`track()` 跟随重定位用同一套三重判据。

  **③ 的隐藏前提：跳转必须真的把键盘焦点交给目标窗口**（T218）。`paneOwner` 读的是 App 级 `kAXFocusedUIElement` = 「当下焦点在哪个 pane」，跨窗口跳转时这**不会自己移动**——`raiseEditorWindow` 原本只设 `AXMain`+`AXRaise`+`AXFrontmost`，窗口到最前了但焦点还在你跳之前那个窗口里，于是 ③ 拿旧窗口某个 pane 的身份去对目标，**永久否决**：无 pane 记忆 → 圈从不出现；有记忆 → 预绘 2s 后被 `armPredictionGuard` 撤回（「显示一下就消失」）。修法是 raise 序列补第四步 `kAXFocusedWindowAttribute`，见 [`jump.md`](./jump.md) 同名小节。**改 raise 序列 = 改这条判据的地基**，两处要一起看。

- **★ 诊断日志 `~/.claude/spectix/ring-diag.log`（`FocusRing.ringLog()`，128KB 自清）**：一次 highlight 的全生命周期各写一行——`arm` / `armWindow`（target、editor pid、`jump=` 跳转还是手点、ring/caption 各自画不画）、`recall hit·miss`（有没有 pane 记忆可预绘）、`present`（`predicted=` 是不是预绘、anchor 窗口、矩形、复用 show 还是 reposition）、`poll HIT` / `poll miss`（**三重判据各自的值**：`report=` token、`pane=` 是不是 xterm textarea、`owner=` 反查出的 shellPid）、`poll GIVE UP`（指定了 pane 却超时 → 什么都不画）、`prediction UNCONFIRMED`（预绘没被确认 → 撤回重跑）、`dismiss reason=`（11 个调用点各带原因 + 圈存活了多久）、`alpha=`（可见性**翻转**时记四个 park 分量）。
  - **为什么必须有**：这条链每个决策都在后台队列里、无任何可见痕迹，「圈没画出来」和「圈从没被 arm」在外部看长得一模一样，T218 的根因（③ 每 tick 否决）**只**表现为 `owner=` 指向你没跳去的那个窗口里的 pane。没有它这个 bug 不可诊断。
  - **成本控制**：`poll miss` 的 pane/owner 查询**每 4 tick 采一次**（~0.5s，attempt 0 必打）——这两个查询是一个 miss tick 里最贵的部分，命中路径不该为诊断付两遍钱；`alpha=` 只在**翻转**时写（track 每 0.2s 一 tick，每 tick 都写会瞬间喂满日志）。
  - 同 `sweepLog`：**写文件，不是 NSLog**——本 bundle 是 ad-hoc 签名，NSLog 到不了 unified log。别退回 NSLog。
- **★ pane 归属：名字不是身份（「高亮全都是默认的灰色 / 点击后不一定能跳对」的修复，改 `resolveOwner` / `paneIdentityCache` / `paneIdentity` 前必读）**：manifest 按**标签名**给 pane 反查 shellPid，而 **Claude Code 把所有「没有任务摘要可显示」的会话都命名为 `✳ Claude Code`**（回合结束 / 等确认 / 刚起都是），`normalize()` 又**故意**剥掉开头那个状态字符（好让同一个终端在状态翻转时还能匹配上）—— 于是 `⠐ Claude Code` / `✳ Claude Code` 一起塌进 `Claude Code` 这**一个 key**，四个活会话共用它。老代码 `pids.first(where: hasStatus)` 永远取同一个候选，后果三连：① 撞名的 pane 全部用那**一个**会话的颜色（一个 idle 会话把正在跑的 pane 画成灰色）；② `desired[pid]` 以 pid 为 key，两个 pane 塌成**一个** overlay，圈可能落在另一个终端上；③ 点行走 `emphasize(shellPid)` 时那个 pid 压根没有 overlay，**点击没有任何落点反馈**。同一个洞还废掉了上一条的 `paneOwner` 三重判据（四个候选都算"命中"）。
  - **修法**：认 AX 描述里的 **`终端 N`**（`终端 2，⠐ Claude Code 运行命令…`，= VSCode 的 terminal instanceId，**窗口内唯一、终端活着就不变**，`paneIdentity` 把它和标题一起解析出来，老的 `paneTitle` 只是它的薄封装），再从**唯一不会说谎的源**学出 `N → shellPid`：extension 的 `active-terminal` token（`focusByPid` 精确按 pid 匹配写的）。两条学习路——① `pinFocusedPane`：点击/跳转时 shellPid 是**行给的、确切的**，直接把当下聚焦 pane 的号钉上（`emphasize` 在 +0.35s / +1.0s 各跑一次，等焦点落定）；② `learnableOwner`：常驻扫描里被动学，要求 **(聚焦 pane 号, token pid) 连续两次一致**才采信。**学不出来就不画**（`resolveOwner` 返回 nil）——猜就是这个 bug 的成因，圈错比不圈更糟。
  - **★ 缓存必须按「窗口」分组，不是按 editor pid**：`终端 N` 在**每个窗口**都从 1 开始，而 **VSCode 所有窗口共用同一个进程 pid**——按 pid 键控时 TB 窗口把 `1 → 自己的 shell` 钉上，`.claude` 窗口的 1 号 pane 就解析成那个外来 pid、过不了候选校验、**一个圈都不画**。故用 `focusedWindowID()`（`kAXFocusedWindowAttribute` → `_AXUIElementGetWindow`）当 key，这才是号码真正的作用域。`lastFocusObservation` 同理带上窗口。
  - **★ 别回退成「按 token 文件 mtime 判沉降」**：曾写成「token 写入满 0.6s 才采信」，听着等价，实测**几乎从不成立**（日志里 `token=-` 刷屏）——聚焦终端和切窗口都会重写 token，而扫描每秒好几次，于是缓存一条都学不到、撞名 pane 全部 unresolved = **完全不出圈**。要判的是**数据稳定**（两次观测一致），不是文件被摸过多久。
  - **陈旧 pin 无需清理**：pin 只在「仍是该 pane 的活候选之一」时才被采纳，所以终端关掉、或窗口重开把计数器归 1，都只会退化成「解析不出」，不会给出错答案。
- **⚠️ 副作用**：首次展开 a11y 树 VSCode 会弹一次「检测到屏幕阅读器，是否启用 editor.accessibilitySupport」通知——点**否**会持久写入设置，之后不再弹（不影响本功能，pane frame 来自 Chromium 树，与该设置无关）。
- **★ 降级：窗口兜底只给「本来就没 pane 目标」的场景（T73「高亮圈住整个 VSCode 页面而不是里面的 terminal」的修复，改 `poll()` 超时分支前必读）**：extension 未装（`targetShellPid=0`）→ 直接圈 VSCode **聚焦窗口**（`kAXFocusedWindowAttribute`，无需渲染树），此时窗口本就是唯一落点；且仅当**没有新 token 指向别的 terminal** 才画（有 → 用户明确去了别处，什么都不画）。**指定了 pane（target > 0）时超时一律什么都不画**——曾经也退化成窗口兜底，于是「点终端 → 随即点进编辑器/侧栏」必翻车：token 只被**别的 terminal** 改写，点编辑器不动它，所以 report 一直"新鲜且等于 target"、而焦点已不是 xterm textarea → 每 tick 都 miss → ~6s 后一个大圈套住整个窗口（`forever` caption 还会把标签永久钉在窗口上），此时用户早就自己找到终端了。**没确认到 pane 就别乱圈**：圈错比不圈更糟。
- **★ 「扩展装了」≠「扩展在跑」，pane 路只认后者（T226/T229，改 `extensionServing` / `paneTargeted` 前必读）**：编辑器只在**窗口启动时**加载扩展，所以每一次全新安装、直到用户重载窗口之前，文件都在磁盘上、却没有任何 extension host 在跑它（反过来也成立：删了文件、host 照样跑到编辑器退出为止，T226 E3 实证）。以前 `paneTargeted` 只看目录在不在，于是这段窗口里每次跳转都：发一个没人读的 focus-request → arm 一个 target > 0 的圈 → poll 28 次全 miss → `GIVE UP` → **什么都不画**，用户读到的是「高亮是坏的」。现在判据换成 `terminals-<hostPid>.json`：每个活着的 host 每 ~2s 重写一份、列出它那个窗口里所有终端的 shellPid（`CompanionExtension.liveManifests()`，`Diagnostics.swift`；host pid 用 `kill(pid,0)` 探活，崩掉的 host 留下的旧文件不算）。**目标 shellPid 在某个活 host 的清单里 → 走 pane 路；装了但不在 → 退回窗口圈（和「没装」同一条路，`target=0`），caption 的任务位换成「按 ⌘⇧P → Reload Window 开启高亮」**，`jump-diag.log` 同时记一行 `extension on disk but no live host lists sh<pid>`。这条不动 `GIVE UP` 的设计（上面那条仍然成立）—— 它只是不再让「没加载」这个状态走进 `GIVE UP`。代价：窗口刚打开的头 ~2s（host 还没写出第一份清单）也会被判成「没在跑」退回窗口圈，接受。启动时那次「重载窗口」弹窗（T231）同样改看这条：编辑器在跑、扩展在盘上、却没有一个活 host → 才弹，且只在真弹了才消耗「每版本一次」的标记 —— 以前升个版本它对已经跑着扩展的用户也弹一次。
- **诊断出口：设置 → 系统权限 →「导出诊断记录」**（`DiagnosticsReport`，`Diagnostics.swift`）：存盘面板选位置 → 写一个纯文本文件并在 Finder 里选中。内容 = 版本 / 系统 → AX 授权 + `axDegraded` → 每个编辑器的「在跑 / 盘上有哪些 `*.focus-*` 目录 / `extensions.json` 里登记了没」→ 每个 `terminals-*.json` 的 host 活没活、多久没写、列了哪些终端 → `active-terminal` / `active-window` / `focus-request` 的值和时间 → hook 登记情况 → 六个自清日志各取最后 400 行。**远程排查高亮，第一句话就是要这个文件**（以前是要 `ring-diag.log`，用户找不到）。不含任何 per-session 状态文件（title 里有 prompt）、账号簿、hook 脚本内容；日志里的项目名按 `jumpDiag` 的既定口径保留。
- **消失时机**：呼吸动画是有限 keyframe（峰-谷-峰-谷-峰-0，最后一程直接淡到 0，`fillMode=.forwards` 停在 0），窗口移除定时在动画结束点（`RingView.lifetime`，从圈画出来那刻起算，不吃定位延迟）——视觉上永远以淡出收尾，不硬切。每次跳转点击走 `highlight()` 重画即重新开始。keyDown 提前消（全局+本地 monitor，arm 在轮询开始时——圈还没画出来你就开打字了直接取消）；**点击落在圈内也提前消**（`shownTarget` 命中 `NSEvent.mouseLocation`——鼠标点确认权限弹窗后黄圈不再赖着呼吸完）；**点圈外故意不消**（找 terminal 时点别的不打断）。Cmd-Tab 走不到 event monitor，靠 `didActivateApplicationNotification`（激活的不是 VSCode → 消）；Space 切换也消，但跳转自身的切 Space 有 1.2s 宽限。
- **★ ring/caption 跟随 terminal 的 Space（改 `show()` 的 Space 处理 / `bindToActiveSpace()` 前必读）**：overlay 三件套（ring / caption / ✕ panel）出生时 `canJoinAllSpaces + .stationary`，钉在所有 Space —— 但这是**临时**的，只为让跳转的 Space 切换（常跨屏）过去一定看得见。副作用若放任：离开目标 Space 后浮在**每个无关 Space** 上（`forever` caption 不自 teardown 时尤其明显）。**修法（跟随而非消失）**：`show()` 把三件套 orderFront 进来后（**alpha 仍是 0**）隔一个 runloop tick 调 `bindToActiveSpace()` —— **`collectionBehavior.remove(.canJoinAllSpaces)` + `orderOut`→`orderFrontRegardless` 重新落座**，之后才跑 0.12s 淡入 → window 从此**只属于 target 的 Space**，macOS 天然管可见性：**切走隐藏、切回 target Space 自动恢复显示**（forever caption 回来还在）。`spaceBound` 保证每次 highlight 只绑一次，`dismiss()` 里 reset。
  - **★ 为何绑在「淡入之前（alpha 0）」（T72「第一次点击闪一下」的修复，改 bind 时机前必读）**：重新落座的 `orderOut`→`orderFrontRegardless` 会把窗口从屏上摘掉一瞬。早先绑在**淡入 completion**（0.12s 后），那一瞬正好发生在 overlay 刚可见之后 = 用户看到的「**显示 → 消失 → 显示**」；重复点**同一个**终端被 `flashFocused` 的 8s dedup 吞掉不重画，所以现象读起来像「只有第一次点击才闪」。改在 alpha 0 时落座，同样的 orderOut 完全不可见，且 canJoinAllSpaces 的泄漏窗口比原来还早关 0.12s。**为何不需要等**：`show()` 跑在跳转 raise + Space 切换**之后**（pane frame 已解析出来 = 此刻 active Space 已是 target），本来就没有要 settle 的东西——当初等淡入结束**唯一**的理由就是「绑定要 orderOut、会打断淡入」，alpha 0 时这个理由不存在（更早的 1.2s 固定 timer 版本则会漏：那 1.2s 内切走，window 仍 canJoinAllSpaces 会浮到无关 Space，T40 二次反馈）。✕ panel 同样改成 alpha 0 出生、跟着同一组动画淡入，否则它会代替圈闪那一下。**不要**改回监听首次 `activeSpaceDidChange`：切换触发时 active 已是**新**（无关）Space，会绑错；且跳转不跨 Space 时根本没有该事件。
  - **`armDismissListeners()` 不再有 Space dismiss hook** —— 切 Space 交给上面的原生 per-Space 可见性；caption 场景仍 `guard !drawsCaption` 跳过打字/点击/切 App（保「常驻、不被打断」）。★ 坑（T40）：该函数曾整段被 `guard !drawsCaption` early-return，caption 场景压根不装任何 dismiss，导致 caption 永久跨 Space 泄漏；先按「切走即消失」（方案 A）修过一版，实测用户要的是「切回要恢复」，遂改为本条的跟随方案。
  - **对照 always-on**：always-on overlay 本就 per-Space（不加 canJoinAllSpaces），切 Space 靠 `kickRescan()` 重扫 AX 树增删；one-shot ring 走的是「临时 canJoinAllSpaces → settle 后绑定」这条不同的路（它有明确的单一 target pane，不需要重扫）。
- **★ 常驻 caption+ring 跟随实时状态（「已经开始跑了 title 还是白色/上一个阶段颜色」bug 的修复，改 `refreshLiveCaption`/`show`/`highlight` 前必读）**：`captionDuration == .forever`（设置里「常驻显示」）时，跳转/点击画出的 **一次性 caption+ring overlay 永不拆除**（`show()` 的 `hold < 0` 不排 teardown），但它的**颜色 + 标题都冻结在创建那一刻**——和 always-on 托管圈不同，它不在任何 recolor 台账里。∴ pane 后来开了新回合（working），圈还是 idle/上一轮的颜色、标题还挂着旧话题。**这才是用户实际走的路**（实测其设置 `ringAlwaysOn=false` + `captionDuration=forever` + `captionOnFocusClick`；always-on 那条 recolor 路他根本没开）。修复：`main.refresh()` 主 hop 每轮调 `TerminalFocusRing.refreshLiveCaption(rows:)` —— 仅当「有常驻 caption overlay 且 `currentTarget>0`（pane 路，window-fallback 跳过）」时，按 shellPid 反查 live row，`status/color/folder/taskTitle` 任一变了就**就地重建 RingView**（换色 + 换标题 + 按 `ringEligibleForCaption && style!=.off` 决定 idle 时摘圈/working 时复圈），没变则不重建（否则每 poll 重启呼吸动画）。`shownStatus/shownAccentHex` 记录已绘制基线防抖；`dismiss()` 只清 `window`，`currentTarget` 残留无害（`window!=nil` 守卫兜底）。

- **★ 常驻 caption 跟随「焦点是否还在这个 terminal」（「我 focus 到别的地方标签还一直显示」bug 的修复，改 `track` 的 `paneFocused` / `applyCaptionFocus` 前必读）**：`forever` 不排 teardown，所以在此之前标签只要不死就一直挂在那块 pane 上——但**「常驻显示」的语义是「只要我人还在这个 terminal 上就一直显示」，不是「永远显示」**。判据两条，全部复用 `track()` 每 0.2s tick **已经算出来的**东西，不新增 AX 开销：① 目标 app 是**前台**（`frontmostApplication.processIdentifier == pid`）；② pane 路还要求焦点**仍解析到那个 pane**（`report == target` + xterm textarea + `paneOwner` 三重判据，即原本决定 `axRect` 的那套，抽出 `paneFocused`；window 兜底路没有 pane 身份，只看①）。任一不满足 → park；两条都回来 → 立刻复原（标签是「我在哪」的路标，点回终端必须马上回来）。三个细节：**(a) 用 alpha 不用 `orderOut`**——回来时的 `orderFrontRegardless` 会把窗口重新落座到**当前** Space，正是 `bindToActiveSpace()` 那条「不许泄漏到无关 Space」要防的；`✕` 是独立收点击的 panel，park 时一并 `alphaValue=0` + `ignoresMouseEvents=true`，否则留一个看不见的方块吞点击。**(b) `shownAt`（圈**画出来**那一刻）起 1s 宽限**——`show()` 跑在跳转 raise 还在 settle 的当口（有一瞬我们不是前台），不宽限就会「刚画出来闪一下」。★ 锚点**必须**是 `shownAt` 不是 `armedAt`（T72 一并修）：`armedAt` 在 `highlight()` **开始**时打点，之后的 pane poll 冷启动可能烧掉数秒（a11y 树首展 1-3s），等 caption 真上屏时 armedAt 宽限早过期 → 第一个抖动的 track tick 就 park → 又是一次「显示 消失 显示」。**(c) 去抖分级**——离开 app 是确凿信号立刻 park；还在 app 内但 pane 解析失败要**连续 2 tick**（0.4s）才 park，单次失败多半是 AX 树抖动。只对 `forever` 生效：定时 caption 自己就淡走了，而光圈（无 caption）活着的意义正是「你满屏找终端时别消失」。

- **★ caption 宽度自适应 + hover 展开全文（改 `addTitlebar` / `pillTextBudget` / `armCaptionHover` 前必读）**：bar 横跨整个 pane，所以**窄 terminal 才是这块的真实场景**。老布局为了让标题视觉居中，**左右各预留一个 ✕ 槽**（`2 * slot`）**再减掉 badge**，剩下多少就原样丢给文字层、**没有任何下限**——窄 pane 上这个余量掉到 ~0 甚至负数，`min(natural, maxWidth)` 于是给出零宽 frame，能截的字也一并没了。
  - **修法 = 固定的让位顺序：✕ 槽 → badge → 标题**。标题**永远最后**，且只截断（`…`）不消失：先扣掉 `padL + slot`，`avail` 若连「badge + `capMinText`(34pt)」都放不下就**直接不画 badge**（图标没了名字反而更糟），剩下的全给文字。**居中变成有条件的**——只在「不需要截断 **且** 整块仍避得开左右两个 slot」时居中，一旦要截断就左对齐 `padL`，把每一点宽度都花在字上。`addCaption` 的入口 guard 也从写死的 `> 90` 换成 `closeSize + 2*closeInset + capMinText`（= 66），与预算算式同源。三种 pill 样式走同一套 `pillTextBudget`（各自的 chrome 不同），`segmented` 另外修了一处：项目段的 `padA*2` 以前没从半宽里扣（长项目名会把任务段挤成 0）。
  - **hover 展开（`expansionPlan` / `captionBody` / `seatCaptionText` / `setCaptionExpanded`）——四种样式统一**：截断了才有东西可露，所以只在 `truncated` 时展开；全文 wrap，最多 `capMaxLines`(3) 行，行数还要过「pane 高度一半」这道闸，**只放得下 1 行时干脆不展开**（同一行重排一次只是抖动，不是「显示全部」）。**一律向下长**：titlebar 从 pane 顶边往下，三种 pill 则改成**顶边定锚**（`placePill` 从 `inset.maxY + 1 + capBand` 减去实际高度反推 y，收起时算出来与旧值分毫不差）——因为 pill 头上只有 24pt margin，overlay 窗口就到那儿为止，往上没有可长的地方。装饰件（红点 / 竖条 / badge / ✕）靠 `yOffset` **钉在第一行**，所以 `closeButtonFrame` 不用跟着变；`accentRule` 的竖条例外，它跟着文字块一起长（否则读起来像只标了第一行）。`segmented` 只有任务段会长，项目段跟着取同一个高度。重排只重画 caption 层（`captionRoot` 摘掉重建，包在 `CATransaction` 关隐式动画里），**不碰圈的动画层**——整个 RingView 重建会把呼吸循环重启。
  - **★ `segmented` 窄 pane 转两行（T181，改 `addSegmented` 前必读）**：左右两段要求**两列各自**都装得下可读文字，而可用宽 `maxW` 低于 **114**（`= capMinText*2 + padA*2 + padB*2`）时怎么分都做不到。老代码把余量丢给任务段、`tkMax < 16` 就**整段不画** —— 窄 pane 上于是只剩项目名；更糟的是 `captionCanExpand` **只在那个分支里赋值**，走 else 时保持 false，`setCaptionExpanded` 直接拒掉悬停 —— 唯一还能读到标题的路被同一个 bug 一起关死了。**修法**：低于阈值改画**一张卡**（上行 accent 项目段 + 下行整宽任务行，收起 45pt 高 / 3 行展开 75pt），任何过得了 `addCaption` 入口 guard 的 pane 都装得下（`maxW > 58` ⇒ 任务行预算 `maxW − padA*2 > 36 > capMinText`）；`tkMax >= 16` 那道 guard 随之成为**可证明的死代码**（stacked 时 >36；side-by-side 只在 `maxW ≥ 114` 且 `segAW ≤ maxW/2` 时走到，⇒ `tkMax ≥ 33`）删掉，`captionCanExpand` 提到分支外无条件赋值。
    - **★ 行数只由 pane 几何决定，绝不看 `captionExpanded`**：hover 若能改变行数，`captionHitRect` 就会在光标底下缩回去 → 展开/收起来回抖。现在展开只让任务行往下长，**顶边和宽度都不变**，展开态 frame 是收起态的严格超集，上一条那个「命中区跟着展开变大 = 天然迟滞」的性质原样继承，`placePill` 一行没动。
    - 触发还叠两道闸：**任务确实会被截**（装得下就不必长高）、**pane 高 ≥ 90**（收起态整块不超过 pane 高一半）。`maxW ≥ 114` 的 pane **逐像素不变**。副作用一条：两行时项目段拿整宽预算，于是 badge 在窄 pane 上反而**回来了**（112pt 的 pane 横向时 `free=34` 砍 badge，两行时 `free=90` 保留）。完整规格与被否方案见 `design/segmented-caption-narrow.md`。
  - **★ 为什么用 mouse-moved monitor 而不是 tracking panel**：overlay 是 **click-through** 的（✕ 那个小 catcher 是唯一例外），标签盖住的那块终端**必须还能点**。任何大到能 track hover 的 panel 都会连点击一起吞掉。故用**被动的** global + local `.mouseMoved` monitor（不消费事件），每次移动做一次矩形判断。命中区是 `RingView.captionHitRect`（caption 自己的 view 坐标 rect，经 `convertToScreen` 换算，四种样式通吃、不用按样式手算），**它跟着展开一起变大 = 天然的迟滞**，不会「展开→鼠标已在新区域外→收起→再展开」抖动。装在 `show()`（并立刻自测一次——标签可能就画在静止的光标底下，之后不会再有移动事件）、卸在 `dismiss()`；`reposition` / `refreshLiveCaption` 重建 RingView 后走 `resyncCaptionHover()`（新 view 一律是收起态，缓存的 hover 标志必须跟着清，否则下一个移动事件判为「没变化」就把悬停中的标签晾在收起态）；`syncOneShotAlpha` 里也调一次，park 期间不可见时收起、回来时重测。
- **titlebar caption 画在圈里**：`titlebar` 样式的标题条**贴在高亮圈内侧顶边**（`bar.y = inset.maxY - 32`），顶部两角圆角 10 与圈的顶角同心贴合，底边 accent 线是它与终端内容的缝。overlay 窗口因此**不再为它多留 32pt 上带**（`topExtra` / `outlineRect` 已删——曾经是「条在圈外、圈把条+pane 一起圈成一个盒」的写法，视觉上标题浮得太高、脱离终端），`show()`/`reposition()`/`refreshLiveCaption` 的 frame = padded pane + margin，标题长短再也不改窗口尺寸；✕ 热区随之落到 `target.maxY - titlebarHeight` 那条带内。
- **样式设置**：`AppSettings.ringStyle(for:)` **每个状态各配一种**（8 选 1：不显示 off / 光晕呼吸 breath / 波纹扩散 ripple / 流光环绕 sweep / 四角对焦 corners / 锁定收束 converge / 霓虹通电 neon / 虚线行军 ants；出厂默认见 `AppSettings.ringStyleDefaults` —— 运行 ripple · 完成 ripple · 需确认 converge · 闲置 breath · 暂停 ants），`highlight()` 和 `show()` 都会读（off 直接跳过）。设置窗口「跳转高亮」卡片带**实时预览**：迷你 terminal 模型上循环回放**真正的 `RingView`**（同类同参，所见即所得），按各样式 `lifetime` 定时重播，窗口关闭即停（`SettingsWindow.swift` `replayRingPreview()`）。加新样式 = RingStyle 加 case + RingView 加 build 函数，设置里自动出现。
- **手动点击终端也闪一次**（`AppSettings.ringOnFocusClick`，默认开，设置里有开关，从属于 ringStyle——off 时两者都不画）：extension 的 `active-terminal` 写入不分跳转/手点，`main.swift` `checkFocusFlash()` 用**独立的 0.3s 轻量 Timer** 盯 token 变化（2.5s 的 refresh 太慢；dedup 状态 `lastFlashToken` 与 `dismissFocusedToast` 的 `lastFocusToken` **各自独立**，同一文件两个消费者互不吞事件），新 token → `flashFocused()`。跳转自己引发的 token 变化由 `flashFocused` 的 currentTarget+8s 窗口去重，不会双重画圈。★ **连点不同终端「下一个不亮」的坑（改 `flashFocused` 前必读）**：`flashFocused` 还有一条「外来 pid + 距 arm <1.5s → 跳过」的 guard，本意只压制**跳转**后 VSCode raise 把焦点恢复到上一个终端的副作用；但它早先无差别生效，导致**手动快速点 A→B**时 B 是外来 pid 且距 A 的 arm <1.5s → B 被吞掉不画圈（用户报的「感觉很卡」）。修复=给这条 guard 加 `armedByJump` 前置条件（`armJump()` 置真、手点走的 `highlight(fromJump:false)` 置假），**只有 jump arm 才压外来 pid**，手点连击每个都立即重画（旧圈 `dismiss()` 0.15s 淡出、新圈 ~300ms 画出，干净利落）。会话终端用状态色；**没跑 Claude 的普通终端一律不画圈**（`checkFocusFlash` 里 rows 查无此 shellPid 就 return）。★ 别再试图把它映射到某个 status：先后踩过两次——映射 `working` → 点普通终端闪蓝（假装有回合在跑）；映射 `idle` → 用户若把 idle 样式设成 ripple/breath 就画出灰白圈（`idle` 语义是「**会话**闲着」，是合法可圈的状态，不是「不是会话」）。配套：`highlight()` 的 `.off` 判定提到 always-on 分支**之前**——.off 的状态不可能拥有常驻 overlay（`recolorOverlays` 会摘掉），提前返回省掉一次白跑的 AX 全树扫描。
- **★ 侧栏聊天面板的焦点只能靠 AX 认（T204 Phase 1 实测结论，改「焦点 → list 同步」前必读）**：终端方向靠 extension 写 `active-terminal`，而**侧栏的 Claude Code 是 Anthropic 扩展的 webview，VSCode 不给第三方扩展「哪个 view 持有键盘焦点」的 API**——我们的 extension 根本感知不到它被点了。负空间也推不出来：焦点移到侧栏后 `activeTextEditor` **仍然保持**上一个编辑器，编辑器和侧栏在 API 层区分不开。∴ 唯一信号源是 a11y 树。**2026-08-09 实测**（VSCode 中文 UI，逐个采 `kAXFocusedUIElement` + 祖先链）四种焦点完全可分：

  | 焦点 | `role` | 判据特征 |
  |---|---|---|
  | 集成终端 | `AXTextField` | `desc` = `终端 N，<状态字符> …`（即 `paneIdentity` 认的那个） |
  | 代码编辑器 | `AXTextArea` | `desc` = `现在无法访问编辑器。…`；up2 `subrole` = `AXCodeStyleGroup`；up3 `desc` = `<文件名>，编辑器组N` |
  | **聊天输入框** | `AXTextArea` | **`desc` == `Message input`**；up2 `subrole` = `AXApplicationGroup` |
  | **聊天消息区** | `AXWebArea` | **祖先链里 `desc` == `Claude Code`**（实测在 up1）；up7 `subrole` = `AXWebApplication` |
  | 文件资源管理器 | `AXRow`(`AXOutlineRow`) | up2 `desc` = `文件资源管理器` |

  - **判据必须是正向白名单，不能用排除法**：编辑器和聊天输入框**同为 `AXTextArea`**，靠 role 分不开；但 `Message input` / `Claude Code` 这两个字符串是 Claude 面板独有的，认它们就不会误伤编辑器、终端、文件树——**即使遇到没采过的第五种焦点形态，也只是不认，不会认错**（同本文档反复出现的那条：认不准就别画/别 pin，错比没有更糟）。
  - **`Message input` 是英文，`终端 N` 是中文**：同一棵树里前者来自 Anthropic 扩展自己的 aria-label（未本地化），后者跟随 VSCode 界面语言。所以这条判据**不随系统语言变**，而终端那条会——别把两者当成同一种可靠度。
  - **已知残余风险**：别的聊天类扩展（如 Copilot Chat）若也把输入框标成 `Message input` 会误判。后果轻微且自限——`focusSession` 的 `rows(containing:)` 查不到该窗口的会话就只会**清掉 pin**，不会 pin 错行。
  - **过渡态会报 `desc=undefined`**：面板刚加载/焦点切换途中，本该是 `Claude Code` 的那层容器可能读到 `undefined`（第一、二轮各采到一次，第三轮稳定后不再出现）。**不要为它加兜底**——它没有任何正向特征，猜就是错的来源；漏认一次的代价只是这一下不跟随。
  - **⚠️ 留给实现的坑：AX 给的是主进程 pid，不是要的那个**。`frontmostApplication.processIdentifier` 是 **Code 主进程**（实测 1464），而聊天行的 `shellPid` 是**扩展宿主**（`Code Helper (Plugin)`）的 pid，两者不同，且一个主进程下每个窗口各有一个扩展宿主。所以 AX 只能回答「焦点在不在聊天面板」，**回答不了「是哪个窗口的聊天」**——那一半得让 extension 出（它的 `process.pid` 就是扩展宿主 pid，`terminals-<pid>.json` 已经在用同一套键法）。两个信号各答一半，谁也别想单干。
- **★ 聊天面板焦点 → 列表 pin 的落地（T204 Session 2，改 `checkChatFocus` / `editorFocusKind` / extension 的 `reportActiveWindow` 前必读）**：终端那条链是「extension 写 `active-terminal` → `checkFocusFlash` 读到新 token → `focusSession(shellPid:)`」；聊天面板这条链是**两半合取**——
  - **AX 答「在不在」**：`editorFocusKind()` 一次 `kAXFocusedUIElement` 读出三种结果（`.terminal` / `.chatPanel` / `.other`）。**一次取元素、三个判定共用**，因为它挂在 0.3s 的轮询上，分开问就是三倍 AX 流量。
  - **extension 答「是哪个窗口」**：`onDidChangeWindowState(focused)` 里写 `active-window` = `<process.pid>:<nonce>`（扩展宿主 pid = 聊天行的 `shellPid`，`main.swift` `discoverSessions` 用 `ppid` 取的就是它）。**激活时若窗口已是 focused 要补写一次**——VSCode 先恢复窗口再启扩展，那个窗口永远等不到 state change 事件。
  - **只做 list pin，不碰 toast/ack、不画圈**（用户 2026-08-09 拍板）。终端那套 ack 敢做是因为它拿的是 extension 的精确报告；这边是 a11y 轮询，**一次误读就会把真的「需确认」红行标记成已看**，代价不对称。圈也不画：侧栏是 webview 圈不准，而且手点的人自己知道点了哪。
  - **★ 压制窗口按「AX 滞后」定，不是按「用户点击间隔」定（`focusTokenAge() > 0.5`）**：刚点完终端时 Electron 的 a11y 树还会短暂报着你离开的那个面板（同本文档「身份对账」记的那个滞后），所以要压一下让 extension 的精确 token 赢。第一版写了 **1.5s**，用户当场报「点了要等一会才高亮」——因为 1.5s 是照着「人可能多快连点」拍的，而它真正要盖住的滞后只有 **100–400ms**。多压的一秒纯粹是白等。**超调在这里还特别便宜**：终端路径 `checkFocusFlash` 跑在同一个 tick 的**后面**，真有点击落下时它的精确 token 会直接覆盖我们 pin 的东西。
  - **★★ chat → 同窗口那个「本来就 active」的终端，扩展是完全静默的（这是用户报的第二个 bug，改重放逻辑前必读）**：窗口焦点没变（同一个窗口）、`activeTerminal` 也没变（**侧栏不是终端**，切走再切回来它一直是那个），于是 `onDidChangeWindowState` 和 `onDidChangeActiveTerminal` **两个事件都不触发**，没有任何 token 写出，pin 就赖在聊天行上不动。点**另一个**终端时 `activeTerminal` 变了才会触发——这就是用户说的「**有时候**没反应」。（`extension.js` 的 `focusByPid` 里记着这个洞的镜像版：对已经 active 的终端调 `term.show()` 同样不发事件。）**修法**：离开面板时把 `lastFlashToken` 清空**强制重放**当前 token——它指的正是那个窗口的聚焦终端，也就是焦点刚落到的地方。⚠️ **必须 gate 在 `kind == .terminal` 上**：从聊天面板点去**编辑器/文件树**时不许重放，否则会把 pin 硬拽到一个用户根本不在的终端上；那种情况 pin 留在聊天行才对（你还没去任何别的会话）。
  - **判终端用 `AXDOMClassList` 里的 `xterm-helper-textarea`，不用本地化描述**——同 `FocusRing` 解析 ring pane 的理由：class 名不随界面语言变，而 `终端 N` 会。
- **★★ pane 身份挂在 VSCode 的一句 aria 文案上，而那句文案会变（2026-08-30 实测，改 `paneIdentity` / `paneDescTails` 前必读）**：终端 pane 的属主是从 `AXDescription` 里读出来的，格式多年是 `终端 N，<标题> 运行命令` / `Terminal N, <title> run command`；VSCode 某次更新把英文那句改成了 **`Terminal N, <title> Run the command: Toggle Screen Reader Accessibility Mode …`**。解析器认的是 `" run command"`，新串里没有这个子串 → **每一个 pane 都解析成 nil**。
  - **它坏起来一声不吭**：AX 走查照跑、pane 照样找得到，只是一个都叫不出名字。实测埋点：`deep axWins=4 onscreen=4 ranked=4` → 四个窗口各自 `containers=1 textareas=2/3/2/1` → **`resolvePanes` 一条都没进到候选比对**。表层现象是「跳转/圈/角标只对你刚点过的那个终端有效」，看起来像身份对账变严了，其实是这一层根本没产出。

  - **⚠️ 这条同时推翻了 T274 当时记下的一个结论**：那份笔记说「背景遍历能找到 pane 但叫不出名字，是因为会话重名」（`containers=3 textareas=7 resolved=0`）。重名确实存在，但那次 `resolved=0` 的**主因是这个解析 bug**——修好之后同样的背景遍历立刻解析出了带任务摘要标题的会话，**不用点、不用跳转**。仍然叫不出名字的只剩真正重名的那几个（都叫 `✳ Claude Code`）。
- **★ 手动点击也要走 pane memo 预测（T292「点了终端图标过去了，但高亮和 title 都没显示」的修复，改 `highlight()` 的 `fromJump` 分支 / `armPredictionGuard` / `applyCaptionFocus` 前必读）**：预测分支原本写死 `if fromJump`，理由是「手动点击时焦点本来就停在那个 pane 上，poll 第一 tick 就确认」——**这条理由只对「点已经看得见的 pane 内部」成立**。用户改用**竖排 tab** 之后，切终端靠的是**点标签列里那一行**：那个 pane 上一刻根本不在屏幕上，Electron 要先建 DOM 再建 a11y 子树，`kAXFocusedUIElement` 这段时间什么都解析不出来。实测 `poll miss` 连打 **12-18 tick = 2.5-4.7 秒**才 `poll HIT`，用户那边的观感就是「点过去了，圈和标题都没出现」——等它真出来，人早就自己找到了，而且中途敲一下键就被 dismiss 掉了。**修法**：`fromJump` 换成 `strictToken`（只排除 paused/interrupt 那条本来就不是用户瞄准的路），点击和跳转一样从 memo 立刻画。证据强度也一样——目标 shellPid 来自 extension 的 `active-terminal` token，精确到 pid。
  - **★ 预测的看护期必须盖过 poll 自己的预算**：`armPredictionGuard` 原来固定 2s。跳转的 poll 通常 0.3s 就确认，2s 绰绰有余；**点击那条路 poll 自己有 28 tick ≈ 6s 的预算**，2s 会在 poll 还在合法运行的时候把圈撤掉、再从 attempt 0 重跑 —— 正是「圈闪一下就没了、过几秒又回来」。看护期存在的意义是**收回 poll 判定为错的圈**，poll 还没开口就撤销什么都没证明。∴ 跳转仍 2s（`jumpPredictionGrace`），点击给 6.5s（`clickPredictionGrace`，= poll 预算 + 余量）。
  - **⚠️ 它治不了的那一半**：memo 只在 pane **被量到过**时才有（pip 扫描 / `warmPaneMemo` 都只量**看得见**的 pane），而藏在别的 tab 后面的终端压根不在 AX 树里。∴ **SpectiX 重启之后第一次切到某个终端，仍然要等那 2.5-4.7 秒**；切过一次之后它就有 memo 了，再切就是 0ms。**不要拿「同一个窗口里另一个 pane 的 rect」去替补** —— 分屏（split）时一个终端组里有并排的多个 pane，那个假设会直接把圈画到隔壁去，圈错比不圈更糟。
  - **★ 焦点落在「终端标签列的那一行」上不算离开这个终端（T293「通过 app 跳转过去后再点一下终端图标，高亮就消失了」的修复，改 `track` 的 `paneFocused` / `focusIsOnTabRow` 前必读）**：竖排 tab 时**点标签列就是「去某个终端」的动作本身**，可这一下把键盘焦点落在 monaco-list 上、不是 pane 的 xterm textarea 上，于是 `paneFocused` 判假、1 秒后常驻 caption+ring 双双 park（日志里 `alpha=0 capPark=true`，而 `host=true offScreen=false` —— 窗口好好的，是焦点判据把它判没的）。**跳转刚落地时最难受**：你落到终端、顺手点一下图标确认自己在哪，正在看的那个标记就没了。修法：pane 判据落空时再问一句「焦点是不是在标签列里」，是就**保持**（但**不挪** —— 行的矩形不是 pane 的矩形）。两种形态都要认：焦点可能是**那一行**（AX 描述 `Terminal N <标题>`），也可能是**那个列表**（这时候描述在「selected 的那一行」上）。身份沿用 pane 那两条（先 `终端 N` 的 pin，再 manifest 候选），**都答不上来就不保持** —— 否则点别人的终端标签会把旧圈留在原地。
  - **★ 焦点停在标签行上也能「首次画出来」（`tabRowPane`，2026-09-29「点了终端图标过去，title 高亮不出来，得再点一下终端才有」）**：上一条只管**保持**已经画出来的圈；T292 的 memo 预测只在 memo 有货时生效。**memo 是内存态，App 一重启就空**，于是重启后第一次点标签行：`recall miss → blank until poll confirms`，而 VSCode 默认 `terminal.integrated.tabs.focusMode = doubleClick` —— **单击行只换 pane、焦点永远留在列表上**，poll 一直 `pane=false owner=nil` 直到 GIVE UP（实测 15:17:38 那次连 miss 到被下一次 arm 顶掉）。修法：poll 里 token 指向目标、焦点却不在 pane 上时，从焦点所在的标签条往上找 `integrated-terminal`，在它下面收 xterm textarea，**按 `终端 N` 的 instanceId 对上行的 `Terminal N`** 取那个 pane 的矩形直接画（日志 `poll HIT via tab row`），顺带把 memo 写上。按编号对、不按标题对，所以重名会话和分屏的另一个 pane 都不会被挑错。
  - **★ 预测未决期间不许 park 常驻 caption**：`applyCaptionFocus` 的 1s 宽限从 `shownAt` 起算，而预测让标签**先于**树解析出来上屏——中间每一 tick 都读成「pane 没聚焦」，于是标签 ~1.4s 就被 park、等 poll 确认了又回来，又是一次「显示 → 消失 → 显示」。∴ `predictedTarget != 0` 且**人还在这个 app 里**时直接 hold；**离开 app 仍然立刻 park**（那是确凿信号，未决的预测不该给标签赖在你已经走开的终端上的权利）。

- **★ 角标（pip）里「谁有权删点」的规则：deep 的沉默不算反证（改 `apply(…authoritative:vouchedFor:)` 前必读）**：deep 全窗口遍历跑完且有产出时才有资格删 pip——这条不够。**逐个 pane 看，「deep 结果里没有它」和整体空结果是同一种二义**：可能真没了，也可能找到了但因为重名没能命名。而 memo 对这个 pane 是**正面陈述**（当初证据单指一个属主时量下来的，每 tick 还要过「宿主窗口在屏 + bounds 没变」两道闸）。于是两条腿会为同一个点打架：memo 建 → deep 删 → memo 再建，日志里是 `pips=2 → pruned-by-deep → pips=1 → pips=2` 每几秒一轮，**肉眼就是那个点在闪**。修法：deep 只能删 **memo 这一 tick 也没认领**的 pid。真关掉终端由 `recolor` 的 `session-gone` 兜（关 pane 就是杀 shell，行会消失），不靠 deep。
- **★ 竖排终端：叠在一起的点只画最前面那颗（`stackedBehind`，T288，改 `syncAlpha` 前必读）**：终端**按 tab 竖着开**（不是 split）时只有一个 pane 可见，其余 pane 压根不在 AX 树里；再叠上「两个 VSCode 窗口停在同一块屏幕位置」，于是**几个会话的 pane 落在同一个几像素的矩形上**（实测三个会话锚点互相差 3pt）。每颗点各自 `order(.above: 自己的宿主窗口)`——窗口彼此错开时这就是背景窗口的点被挡住的机制，可**窗口完全重合时它们互相挡不住**，全都堆在同一个角上糊成一团。**修在画的那一层，不修在量的那一层**：那些 pane 的坐标全都是真的，只是同一个位置只该有一颗点。判据 = 宿主窗口的 z 序，**最前面的那个赢**（= 你眼睛真正看得见的那个终端），其余**只是 alpha 归零、不删**——窗口一提到前面点立刻回来，不用等重扫。`stackSlop=16pt` 卡在 tab 行距 22pt 之下，∴ 相邻两行永远不会被当成一堆。
- **★ 同一个窗口里叠在一起的角标，按「标签列的 selected 行」挑，不是按 pid（T295「我在第 2 个没在跑的终端上，左上角还显示在运行」的修复，改 `stackedBehind` 前必读）**：pane memo 的三道闸只问「宿主窗口在不在屏、动没动」，**从来不问「这个 pane 还是不是当前显示的那个」** —— 于是竖排切 tab 之后，切走的那几个终端的 pane 点全都还在，和当前那个**落在同一个矩形上**（实测一个窗口里四个 pane 点全在 `-399,2425` 附近）。原来的并列判据是 `pid 小的赢`，纯属随机：用户人在一个闲置终端上，读到的是藏在它后面那个正在跑的终端的蓝点。**修法**：`readTabRows` 顺手记下每个窗口标签列里 `selected` 那一行属于谁（`selected` 才是「当前显示的终端」，`focused` 只是键盘光标在列表里的位置，两码事），叠在一起时**只留它**；连它都还没有点，**整堆一起藏掉**（宁可不画也不画错的颜色）。
  - **★ 这条只对「和同窗口另一个 pane 重合」的点生效，别放宽（分屏会瞎）**：**split 分屏同时显示两个 pane，却只有一行是 selected**。好在那两个 pane **矩形不同**，天然不会被判成一堆；一旦把判据放宽成「这个窗口里所有非 selected 的 pane 点」，每个分屏都会瞎掉一半。
  - **诊断**：`pip-diag.log` 的 `stacked hidden=<n> of <m> showing[w173=<pid>,…]` 一行同时给出「藏了几个」和「每个窗口以为自己在显示谁」，下次再报「角标颜色不对」照这行看就够。
  - **★ 落在标签列上的 pane 点一律藏（`stackedBehind` 的 ⓪ 步，2026-09-29「两个角标叠在一起」）**：标签列在**左侧**时，窗口从一个终端变成两个会**多出**标签列，所有 pane 整体右移一个列宽 —— 但宿主窗口 bounds 没变，memo 三道闸照样放行旧矩形。于是切走的那个终端的 pane 点还留在老位置，正好压在标签列自己那一行的徽章上（实测 `3589@7,972` 与 `3589T@3,976`，同窗口当前 pane 在 `@53`）。它不和当前 pane 重合，① 认不出是一堆。判据：pane 点的圆心落进同窗口 tab 行矩形的并集 → 藏。活着的 pane 不可能和标签列重叠，所以不会误伤分屏。⚠️ 这只兜「标签列冒出来」这一种窗口内布局变化；拖面板分隔条之类的同样会让隐藏终端的 memo 过期，那类没兜（T328）。

- **★ 终端标签列表上的状态徽章（`PipKind.tab` / `readTabRows` / `tabLists`，T288）**：竖排开终端时**只有一个 pane 看得见**，其余终端的状态在屏幕上没有任何落点——除了左边那条**终端标签列**。∴ pip 的台账改成按 `(shellPid, kind)` 键控，pane 点和 tab 徽章共用**同一套**上色 / 跟随窗口 / z 序 / 去堆叠机制，只有两处不同：几何（徽章挂在行内那个 17pt 终端图标的右下角，`min(行宽/2, 19)` 让它在**窄条**和**拖宽后**都落在图标上）和点的直径（9 vs 11）。**身份沿用 pane 那一套**：行的 AX 描述是 `Terminal N <标题>`，和 pane 的 `终端 N，<标题> 运行命令…` 同源，∴ 走同一个 `resolveOwner`，**认不出属主一样不画**。
  - **★ 列表元素必须缓存，不能每次重找（改 `tabLists` 前必读）**：找那条列表要走一趟树，而 deep 扫是**被节流 + 退避**的（全部 pane 都放好了就完全不再 deep），可**行会动**——滚动、开/关一个终端、把标签条拖宽，都会让行换位置。只按 deep 的节奏量，徽章几分钟后就飘到别的行上去了。∴ deep 时只负责**找到并缓存**那个 `monaco-list-rows` 元素，之后**每一趟扫描（含浅扫）**都拿它重读一次子元素——代价是一次 children 调用，换来行几何始终新鲜。
  - **★ 为什么是「盖一颗点上去」而不是「把 VSCode 那个图标染成状态色」（2026-09-03 查证，别再重查）**：**做不到**。`vscode.Terminal` 的 `color` / `iconPath` **只能在 `createTerminal()` 那一刻指定**，接口上全是只读、没有 setter、也没有 proposed API；命令 `workbench.action.terminal.changeColor` 虽然能用 `executeCommand` 调、也能用参数指定作用在哪个终端，但它内部固定弹交互式 quick pick，**不接受颜色参数**——想加这个能力的 [PR #239973](https://github.com/microsoft/vscode/pull/239973) 已被维护者 Tyriar 于 2025-10-27 明确拒绝（"No plans to support args for this command"）。OSC 转义序列（iTerm2 那种 tab 上色）VSCode 也不支持。而 Claude Code 的终端是**用户自己开的**，不是我们扩展建的，∴ 连「创建时指定」这条唯一的路都用不上。overlay 是唯一可行解。
  - **∴ tab 徽章的修剪权和 pane 点相反**：pane 那条「deep 的沉默不算反证」是因为 pane 贵、量不全；tab 行每趟都整读，`tabsFresh` 为真时**读回来的就是全部**，没读到 = 那个终端关了、或者面板被收起来了，**该删就删**。这也是「收起终端面板后徽章不会赖在编辑器上」的实现方式。
- **★ deep 的退避要看「有没有进展」，不是「有没有产出」**：`deepMisses` 原本在 `produced`（这次扫出至少一个 pane）时清零。一个窗口里只要有一个能解析的会话，每次 deep 都 `produced=true`，计数器永远清零 → **对着两个永远解析不出来的重名会话，每 5 秒买一次全窗口树遍历**，正是「always-on 只敢做 dev-only」的那笔开销。判据换成**这次有没有把一个原本没点的会话变成有点**（扫前记下 `unplacedBefore`，扫后看有没有谁拿到了 pip）。
